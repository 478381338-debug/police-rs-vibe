# AI 协作开发证据（传智杯 Vibe Coding）

本目录记录本项目在 ZCode 中“用 AI 修改程序”的真实过程。三条核心迭代都保留了用户 Prompt 原文、AI 的诊断与改动、运行验证结果，以及可回查的会话 ID 和消息序号。

## 0. 先说明：仓库历史是重建的

本项目在 ZCode 中开发时没有启用 Git（会话开始时 `git log` 为空）。为了满足赛道对细粒度提交历史的要求，2026-11-17 在最终代码上按功能模块重建了提交序列：

- 每个提交对应一次真实的 AI 协作会话或一个可独立说明的功能模块；
- 提交信息里写明对应的 `session_id`、消息 `seq` 和用户 Prompt 摘要；
- 原始对话已导出到 `docs/ai-collaboration/raw/`，评委可按序号逐条核对；
- 重建不改变任何代码内容，也不把“让 AI 想方案”的阶段算作代码提交。

这样做是为了让过程可核对，而不是伪造一段不存在的提交时间线。

## 2. 为什么是这三条

- **都是“改程序”，不是“想思路”**：每条都从明确的实现/修复指令开始，AI 的动作是读代码、定位根因、编辑文件、运行验证。
- **覆盖不同技术面**：迭代 1 是后端检索算法 + 前端交互；迭代 2 是 3D/可视化 + 网络仿真数据；迭代 3 是真实遥感数据、坐标修正、工作区与权限。
- **都有可复现的验证**：不是“看起来好了”，而是有具体查询、接口返回、页面尺寸、远程部署结果。
- **都有返工**：迭代 3 记录了用户两次说“没有/刷新没用”，AI 如何从“浏览器缓存”误判纠正到“旧后端进程未加载新路由”，这是赛道特别想看的“如何引导 AI 修 Bug”。

## 5. 边界

- AI 生成的代码均经过人工审阅和运行验证，但本项目不是“AI 全自动生成后直接上线”；人工负责目标、验收标准、边界判断和最终取舍。
- 6G 时延/带宽/丢包/切片配额是数字孪生仿真值；变化检测是规则与多特征算法原型，不是训练好的深度学习模型。
- 法条库是 17 条草稿，`review_status=draft_requires_legal_review`，引用前必须经法制审核。
- 烟台试点是单点、非实时、10 m 影像，不生成“违法概率”，不替代现场核查。
